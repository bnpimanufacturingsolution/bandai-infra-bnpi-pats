# Template Auth API Curl Guide

Base URL example:

```bash
export BASE_URL="https://adam-auth-431713067666.asia-southeast1.run.app"
export TOKEN="YOUR_ADMIN_BEARER_TOKEN"
```

Windows PowerShell:

```powershell
$env:BASE_URL="https://adam-auth-431713067666.asia-southeast1.run.app"
$env:TOKEN="YOUR_ADMIN_BEARER_TOKEN"
```

## Superadmin shortcut

Current superadmin credentials you provided:

```text
email: super@admin.com
password: password123
```

Quick login:

```bash
curl -X POST "$BASE_URL/api/auth/login" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "super@admin.com",
    "password": "password123"
  }'
```

The login response includes a token in:

```text
data.token
```

Example response shape:

```json
{
  "status": "success",
  "message": "Logged in successfully",
  "data": {
    "id": "USER_ID",
    "email": "super@admin.com",
    "organizationId": "ORG_ID",
    "role": "admin",
    "roleId": "ORGANIZATION_ROLE_ID",
    "token": "YOUR_BEARER_TOKEN"
  }
}
```

After login, use:

```text
Authorization: Bearer <data.token>
```

## Important behavior

- `organization`, `role`, and `user` IDs are auto-generated by Prisma/Mongo.
- You cannot send a custom `id` in `POST /api/organization`, `POST /api/role`, or `POST /api/user`.
- If you need the created ID, read it from the create response and reuse it.
- `POST /api/organization` auto-creates organization-level `admin` and `member` roles for that org.
- `POST /api/auth/register` supports `roleId + organizationId` and internally maps that to the matching organization role.
- `POST /api/user` and `PATCH /api/user/:id` support `roleIds`, so you usually do not need to manually map role IDs in HRIS.

## Recommended flow for HRIS

1. Create organization.
2. Create app roles if needed.
3. Register or create users using `roleIds` or `roleId + organizationId`.
4. Patch user metadata from HRIS after user creation.

## 2. Create organization

This returns the new `organization.id` plus generated org roles including `organizationRoleId`.

```bash
curl -X POST "$BASE_URL/api/organization" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme HRIS",
    "code": "ACME-HRIS",
    "description": "Acme organization",
    "branding": {
      "primaryColor": "#1D4ED8",
      "logoUrl": "https://example.com/logo.png"
    }
  }'
```

With app subscriptions on create:

```bash
curl -X POST "$BASE_URL/api/organization" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme HRIS",
    "code": "ACME-HRIS",
    "description": "Acme organization",
    "appIds": [
      "PUT_APP_OBJECT_ID_HERE"
    ]
  }'
```

## 3. Update organization

You can change base fields and also replace app subscriptions by sending `appIds`.

```bash
curl -X PATCH "$BASE_URL/api/organization/PUT_ORGANIZATION_ID_HERE" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Acme HRIS Updated",
    "code": "ACME-HRIS",
    "description": "Updated org details",
    "appIds": [
      "PUT_APP_OBJECT_ID_HERE"
    ]
  }'
```

## 4. List organizations

```bash
curl -X GET "$BASE_URL/api/organization?document=true&count=true&pagination=true&page=1&limit=20" \
  -H "Authorization: Bearer $TOKEN"
```

## 5. Get one organization

```bash

  -H "Authorization: Bearer $TOKEN"
```

## 6. Create role

Use this for reusable roles. If you want the role attached to an app, send `appId`.

```bash
curl -X POST "$BASE_URL/api/role" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "hris-hr-manager",
    "description": "HR manager role",
    "scope": "APP",
    "isDefault": false,
    "appId": "PUT_APP_OBJECT_ID_HERE"
  }'
```

Organization-wide role example:

```bash
curl -X POST "$BASE_URL/api/role" \

  -d '{
```

## 10. Register user through auth API

This is the closest match to your seeder flow.

If you already know a reusable `roleId` and `organizationId`, the API will map it to the proper org role internally.

```bash
curl -X POST "$BASE_URL/api/auth/register" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "employee1@acme.com",
    "userName": "employee1",
    "password": "Password123!",
    "organizationId": "PUT_ORGANIZATION_ID_HERE",
    "roleId": "PUT_ROLE_ID_HERE"
  }'
```

If you already know the exact `organizationRoleId`, send that instead:

```bash
curl -X POST "$BASE_URL/api/auth/register" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "manager1@acme.com",
    "userName": "manager1",
    "password": "Password123!",
    "organizationId": "PUT_ORGANIZATION_ID_HERE",
    "organizationRoleId": "PUT_ORGANIZATION_ROLE_ID_HERE"
  }'
```

## 11. Create user directly with `roleIds`

This is better if you want to avoid role-mapping logic in HRIS.

Send `organizationId` plus `roleIds`, and the API resolves matching organization roles for that org.

```bash
curl -X POST "$BASE_URL/api/user" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "email": "employee2@acme.com",
    "userName": "employee2",
    "password": "Password123!",
    "status": "active",
    "loginMethod": "email",
    "organizationId": "PUT_ORGANIZATION_ID_HERE",
    "roleIds": [
      "PUT_ROLE_ID_HERE"
    ],
    "metadata": {
      "employee": {
        "id": "EMP-001"
      },
      "requirePasswordChange": false
    }
  }'
```

## 19. Suggested HRIS integration strategy

If your current seeder is annoying because you keep maintaining a local role map, use one of these:

### Option A: use `roleId` on register

- Create roles once in auth service.
- Store auth `role.id` in your HRIS config table.
- Call `POST /api/auth/register` with `organizationId + roleId`.
- Let auth service resolve the organization role mapping.

### Option B: use `roleIds` on user create/update

- Create roles once in auth service.
- Store auth `role.id` in your HRIS config table.
- Call `POST /api/user` or `PATCH /api/user/:id` with `organizationId + roleIds`.
- This is the cleanest way to avoid hardcoded `ROLE_IDS` maps in your seeder.

## 20. What to store in HRIS

Recommended values to persist on your side:

- `organization.id`
- `role.id`
- optional `organizationRoleId` if you need exact app/org assignment control
- `user.id`

Minimum useful mapping table:

```text
hris_role_key              auth_role_id
hris-hr-manager            65f0...
hris-hr-user               65f1...
hris-employee-manager      65f2...
hris-employee              65f3...
hris-timekeeper            65f4...
```

That is enough to stop hardcoding Mongo IDs in seed files.
