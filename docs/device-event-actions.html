DeviceEvent actions — trigger → storage → post-effect

What happens when an event lands from the SDK callback (or the same /api/hikvision/callback route). Full text: DEVICE_EVENT_ACTIONS.md.

1. Shared entry

Hikvision panel→ HCNetSDK listener→ POST /api/hikvision/callback→ DeviceEvent write→ device-event:saved socket

logSearch / UserInfo run only as follow-up on that callback path when the first ACS packet has no plain person id — not a separate invent-people service.

2. Identity fields (your model)

FieldValue for person 15
DeviceUser.vendorUserId15
DeviceEvent.employeeNo (schema String?)15
Employee.deviceEmpId15 plain
Employee.employeeId00015 display/org only

3. Three operator events

onUserCreate → USER_CREATED

1. Panel creates person 15
↓ SDK ACS (typed minor or major=3)
2. Callback saves DeviceEvent
↓ resolve plain id (fast or logSearch+UserInfo)
3. DeviceUser vendorUserId=15 + raw UserInfo metadata
4. If Employee.deviceEmpId === "15" → link FKs MATCHED
5. Socket (again if resolved later)
DeviceEvent W/U DeviceUser W/U Attendance —

onEnrollUser → FINGERPRINT_ENROLLED

1. Panel enrolls FP for 15
↓ SDK / logSearch addFp leaf
2. DeviceEvent FINGERPRINT_ENROLLED
3. DeviceUser 15 metadata / numOfFP
4. Templates stay on DeviceUser custody (not event payload)
5. Socket
DeviceEvent W/U DeviceUser U Attendance —

onAttendanceTap → TAP

1. Person 15 verifies OK (major=5)
↓ SDK callback with plain employeeNo usually
2. DeviceEvent TAP
3. Lookup DeviceUser / deviceEmpId=15
4. If linked → Attendance CREATE/UPDATE
5. Socket
DeviceEvent W/U DeviceUser lookup only Attendance W/U if matched

4. First packet often SYNC_SIGNAL

major=3 / operation-sync

SDK says “operation happened” without plain person. Callback still writes a row + socket, then multipass logSearch creates typed USER_CREATED / FINGERPRINT_ENROLLED.

DeviceEvent SYNC_SIGNAL later typed DeviceEvent rows DeviceUser after plain resolve

5. Storage matrix (post-action)

eventAction Trigger (code) DeviceEvent DeviceUser Attendance
SYNC_SIGNAL major=3 / OBSERVED_OPERATION_* Write; often IGNORED while resolving — —
USER_CREATED MINOR_ADD_USER_INFO / addUserInfo leaf Write; employeeNo→15 Upsert vendor 15 + raw metadata —
USER_UPDATED MODIFY_USER_INFO Write Update metadata —
USER_DELETED CLR_USER_INFO / clearUserInfo Write inventory may lag —
FINGERPRINT_ENROLLED ADD_FINGER / addFp leaf Write Update credentials —
FINGERPRINT_UPDATED/DELETED MOD/DEL finger minors Write Update —
CARD_* card minors Write Optional update —
TAP auth pass / minor 38 Write Lookup only Write if employee matched
TAP_REJECTED auth fail minors Write Optional lookup —

6. status (BNPI PATS result) vs eventAction

statusMeaning after processing
RECEIVEDJust saved
IGNOREDNon-attendance without identity yet, or missing employeeNo on tap
UNMATCHEDPlain person known; no Employee.deviceEmpId match
MATCHEDEmployee linked (enroll/user path)
ATTENDANCE_CREATED / UPDATEDTap wrote attendance
FAILEDError

7. End-to-end text diagram

PANEL action
    │
    ▼
HCNetSDK alarm_callback
    │  build JSON: source=EN_HCNETSDK_ALARM, major, minor, employeeNo?, actionCode
    ▼
POST /api/hikvision/callback
    │
    ├─ save DeviceEvent { eventAction from taxonomy, employeeNo?, source, payload }
    ├─ emit device-event:saved
    │
    ├─ if TAP path:
    │     lookup DeviceUser(vendorUserId) / Employee(deviceEmpId plain)
    │     maybe Attendance write → status ATTENDANCE_*
    │     emit again
    │
    └─ if USER / ENROLL / SYNC_SIGNAL path:
          if major=3 → scheduleOperationLogResolve (logSearch leaves)
          if plain employeeNo → DeviceUser upsert + raw metadata
          status MATCHED | UNMATCHED | IGNORED
          emit again when identity lands

8. Schema enum reference

DeviceEventAction: TAP, TAP_REJECTED, USER_CREATED/UPDATED/DELETED, FINGERPRINT_*, FACE_*, CARD_*, SYNC_SIGNAL, SYNC_IMPORTED, LISTENER_RECEIVED, UNKNOWN.

DeviceEventSource: EN_HCNETSDK_ALARM, HIKVISION_CALLBACK, ZKTECO_EVENT, EN_SYNTHETIC_KIOSK_TAP.
