Hikvision callback event flows

What really happens when the physical terminal fires an ACS alarm that the HCNetSDK listener posts to POST /api/hikvision/callback. Three event families: User create, Enroll (fingerprint), Attendance tap.

1. Shared live path (always)

Hikvision panel→ HCNetSDK alarm callback→ Listener posts JSON→ /api/hikvision/callback→ DeviceEvent + socket

Multipass logSearch / UserInfo is only a follow-up on the same callback path when the first ACS packet has no plain person id. It is not a separate product poller inventing people.

2. Your identity model (must stay true)

Where Field Example value Meaning
Physical device / UserInfo employeeNo 15 Plain person number typed/created on terminal
DeviceUser (inventory) vendorUserId / employeeNo 15 Same plain device person id + raw UserInfo metadata
DeviceEvent (ledger) employeeNo 15 Plain id when resolved (never leave opaque as the label)
Employee (HRIS) deviceEmpId 15 Plain device person id — same as vendorUserId (NOT padded)
Employee (HRIS) employeeId 00015 Business / display code (may use leading zeros); not deviceEmpId
DeviceEvent schema employeeNo String? Yes — optional string column for plain device person id
Op log only opaque token QVEwgvx/…== Privacy id in logSearch — map via DevicePersonToken, do not show as employee no.

Match rule: device plain 15 links when Employee.deviceEmpId === "15" (exact plain). Also try Employee.employeeId pad variants (e.g. 00015) for org codes only.

3. Three event families from the callback

onUserCreate

Device user management — person added on terminal (Hikvision major operation / addUserInfo).

1. Hikvision — panel creates person 15
↓ ACS alarm (may be major=3 empty plain, or MINOR_ADD_USER_INFO)
2. Listener → callback — save DeviceEvent USER_CREATED (+ socket)
↓ resolve plain person id
3. DeviceUser upsert — vendorUserId=15 + rawPayload / vendorMetadata from UserInfo
4. Link Employee — if deviceEmpId === "15" (plain) → set FKs + MATCHED; employeeId may display as 00015
5. Socket again — UI shows User 15 (or employee name if linked)

onEnrollUser (fingerprint)

Credential enroll on existing/new person (addFp / fingerprint management minors + logSearch leaves).

1. Hikvision — enroll FP for person 15
↓ ACS alarm + often opaque op log
2. Listener → callback — DeviceEvent FINGERPRINT_ENROLLED (+ socket)
↓ same plain-id resolve as create
3. DeviceUser — ensure row 15; refresh UserInfo counts (numOfFP) into metadata
4. Link Employee — same plain deviceEmpId === "15"
5. Templates — raw FP bytes stay encrypted on DeviceUser custody plane, not on DeviceEvent

onAttendanceTap

Access success (major=5 auth pass) — attendance punch, not user inventory create.

1. Hikvision — person 15 taps (FP/face/card)
↓ ACS alarm with plain employeeNo when available
2. Listener → callback — DeviceEvent ATTENDANCE / TAP
3. Resolve person — DeviceUser(15) first, else Employee.deviceEmpId pad match
4. If matched — create/update Attendance + timesheet projection
5. Socket — live Device Events row; does not create DeviceUser unless missing and plain known

4. onUserCreate — required product model (your expectation)

Must happen for create on one device (e.g. TEST A)

  1. Callback receives the create (directly or via major=3 → logSearch leave addUserInfo).
  2. DeviceEvent saved with action USER_CREATED and eventually plain employeeNo = "15".
  3. DeviceUser created/updated for that device: vendorUserId = "15", employeeNo = "15", plus raw vendor metadata (rawPayload / vendorMetadata from UserInfo/Search).
  4. Employee match: primary key is plain Employee.deviceEmpId === "15" (same as device). Employee.employeeId may be 00015 for display/org code. On match set FKs → status MATCHED / ACTIVE.
  5. If no Employee with that pad: DeviceUser stays UNMATCHED; event still shows User 15 (device person), not HRIS employee name.
  6. Socket so Device Events updates without refresh; Device Users list can open deviceUserDetails=15.
